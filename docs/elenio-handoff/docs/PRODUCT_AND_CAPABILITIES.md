# Product north star and capability map (latest decisions)

**Elenio AI Workspaces — Enterprise Agentic Engineering Platform.** Build, orchestrate, govern, optimize and deploy intelligent business systems. It is Elenio's internal solution factory and an enterprise product licensable on-premises. Outcome is a functional customer-specific agentic workspace, not a chatbot or a workflow picture. AI is used only when useful; combine deterministic logic, agent reasoning, service calls and human authority. Comparable product category: Dataiku-like engineering environment focused on agentic business systems (not generic data science platform). n8n is an interaction benchmark, not a replacement runtime. Two audiences: engineering builders and business operators. Delivery: Elenio managed, customer self-hosted app/runtime, complete private platform, co-build. No cross-tenant reuse of secrets, data or restricted content.

## Object hierarchy and UX mental model
Organization/tenant → workspace/security boundary → project/solution → one or more workflow definitions → immutable versions → cases/runs. Shared libraries hold agents, skills, tools, knowledge references, model deployments, approved connectors, domain packs. Versions pinned; published data immutable except operational state. Case artifact output is versioned, source-cited; review and approval separate. Control Plane is identity/entitlement authority. Keep source of truth by service, not duplicated local state. Distinguish business workflow execution vs agent internal tool iteration vs UI display layout. A template is reusable blueprint, not data or an active run. A domain pack binds workflow, agent keys, artifact types and case navigation. A case/run does not imply a project draft.

## Master journey and success conditions
- Discover: capture goal, current conventional process, costs/volume, constraints, approvals, SLA, security/data location, intended business UI. Ask meaningful clarifications; mark assumptions and open requirements. Chat, file upload or manual input; no forced chat.
- Architect: capability search before recommending new agents, generate requirements, workflow topology, input/output contracts, dependencies, agent role/skills/model suggestions, KMS and integrations, evidence and approval rules, case output and design cost. Human editable/diff acceptance. Explain why each agent is needed. Resolve requirements and provide readiness.
- Build: choose blank canvas, AI generated blueprint or reusable template/import. Edit topology, bind agents/skills/tools/KMS/model and connectors. Explicit `next` and config, conditions and governance. Save drafts, validate, surface diagnostic per node; version pin dependencies.
- Validate: sandbox agent and workflow test with sample data, choose success/exception/parallel/approval cases, inspect execution trace and expected vs actual, measured cost when available. Compare model versions on same dataset, critical gates; invalid output/unknown evidence goes to fail or review. Production publish separate from test.
- Release: independent review (domain and AI Ops where agent release requires), workflow valid publish by authorized human, KMS steward publication, release target/env configuration, validate dependencies/secrets/privacy and approved models, deploy customer runtime or full platform; smoke tests before declaring running. Do not conflate UI manifest with deployment.
- Operate: customer app intake forms/documents/chat, case lifecycle, task/approval inbox, agent outputs/cited sources, draft revision loop before independent approval, timeline, stale artifact propagation, exceptions; operations engineer inspects redacted traces, token/latency/cost, budgets and SLA; user may request changes to approved workflow version.
- Optimize/reuse: economics vs conventional baseline, compare model quality/cost, identify bottlenecks/retries, version changes through gates, save sanitized template or capability; ongoing cases pinned to prior version.

Independent entry journeys: chat-to-solution; manual canvas; clone/import template; create/manage agents or skills; knowledge ingestion/retrieval; API/MCP integration; evaluate model/agent; deployment/monitoring; business case operation; administration. All lead to same authoritative project and runtime data when applicable. Full detailed A–J journeys and requirements in original PRD v1 extraction, screen specs S01–S16 and UAT; this addendum supersedes obsolete navigation/visual concept and extends Model Hub, Economics, Case Workspace and verified contract constraints.

## Showcase scenarios
### Vendor Payment (proposed pilot, not verified upstream pack)
Invoice input via email/upload → Document Intelligence extraction (invoice, PO, line amount/currency/vendor, evidence) → deterministic ERP purchase-order/receipt check → condition matched? yes skip exception agent; no route Exception Analyst using scoped Finance policies → human finance review/approval (independent, authorized) → post to ERP only if approved and validated; rejection/revision or hold safely; verify reconciliation. Never let an agent authorize payments. Add a parallel example (document check and vendor lookup, join before approval). Fixed fixture data only in prototype; actual external connectors must be explicit sandbox/non-production until approved. Cost depends on match rate, attempts, reviewer time; show both scenarios.
### Recruitment (proposed pilot)
Candidate CV/doc intake → extraction & structured job-fit evidence according to approved job requirements → HR human review, revision when required → scheduling/ATS via approved integration; no auto rejection based solely on AI. Exclude protected traits and irrelevant sensitive data; ensure privacy and permissible data retention. Human decision and audit. Use consistent business app screens: queue, candidate case, evidence, tasks, decision.
### Solution Engineering / SIM Tender (source-backed domain pack)
`sim.tender` latest observed v1.3.0 binds Flowcase `sim-tender`, six specialist agents `sim.intake`, `sim.solution_matching`, `sim.design`, `sim.standard_project`, `sim.cost_challenge`, `sim.proposal`, plus `sim.case_intake`. Intake chat + RFP/KAK PDF/OCR. Artifacts: requirement register, fit-gap, design options, work breakdown, cost findings, proposal sections. Case owner review and feedback -> agent re-runs -> submission to appropriate independent gate reviewer; actual G0–G5 sequence/policy from source, not invented. Cited sources, tasks, history and AI activity. Domain pack startability depends on published versions and actual runtime bindings. Do not publish internal/customer data as a showcase. Genericize sample content and keep existing pack contracts. Contract Review and PoC pack fixtures in repo may not be startable; show status, do not pretend working.

## KPIs
Time-to-first-valid-workflow, time-to-first-successful case, reuse ratio, quality/eval pass rate and critical failure counts, human touch time, successful completed cases / attempted, cost per attempt AND completed case, retries, queue and p95 latency, approval policy violations, deployment success and rollback, business value from approved baseline. No fabricated targets; define evidence, units and time window. Product acceptance: real authorized integrated pilot, repeatable deployment, quality/security/finance approval and supportable handover, not just good visual prototype.
